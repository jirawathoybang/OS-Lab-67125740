1. FIFO vs LRU (Phase 2):

From the results of `page_replacement.py`:
- FIFO produced 9 page faults, while LRU produced 7 page faults with 3 memory frames.
- I observed that FIFO removed Page 2 when Page 5 needed to be loaded because Page 2 had entered RAM first.
- LRU removed Page 3 instead because Page 3 had not been used for the longest time, while Page 2 had been accessed more recently.
- When Page 2 was requested again, FIFO experienced another page fault, but LRU could access it directly from RAM.
- From this experiment, I learned that LRU considers recent page usage, while FIFO only considers the order in which pages entered memory. This helped LRU reduce page faults for the given reference string.

2. Understanding Thrashing (Phase 3):

Based on my observations from `ai_thrashing.py`:
- Scenario 1 processed data directly in RAM and took 0.8898 seconds.
- Scenario 2 simulated Thrashing by repeatedly reading and writing data through a disk file. It took 1.9318 seconds.
- Scenario 2 was approximately 2.17 times slower than Scenario 1.
- I observed that Scenario 2 had additional file operations, while Scenario 1 processed data directly in RAM.
- From this experiment, I understand that Thrashing occurs when the system spends too much time moving data between RAM and disk instead of performing useful processing. Repeated disk operations can significantly slow down the system.

3. AI Engineering Decision:

If my AI training program starts Thrashing because RAM is full, I would reduce the `batch_size`.
- A smaller batch_size means the model processes fewer training samples at the same time.
- This reduces the amount of RAM required during each training step, leaving more memory available for the system.
- With lower memory usage, the operating system has less need to move data between RAM and disk.
- I understand that reducing batch_size does not increase the actual RAM capacity. It helps the AI training program use the available memory more efficiently and reduces the risk of Thrashing.
